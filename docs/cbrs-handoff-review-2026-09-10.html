CBRS scraper handoff review

An account of what it took to run the contractor-delivered scraper for the Conservador de Bienes Raíces de Santiago (CBRS) portal, every problem found along the way, what was fixed, and what the system actually delivered against a request for 30 inscriptions with three portal accounts.

Review dates 10–11 Sep 2026 Host Ubuntu 24.04 workstation, no background service Code scrapper-portal-conservador at eee1ac0 + local fixes Times Chile local (UTC−3)
Summary

It works end to end, but it delivered 11 of 30 cases, and at the observed limits it cannot reach 30 in a day with three accounts.

Login, search, page download and PDF assembly all work: 13 valid PDFs came out of the review (11 of the 30 requested cases plus 2 earlier test cases). Getting there required six fixes and workarounds to the delivered setup. Three things then capped the volume: the portal stopped each working account after 7–9 searches, not the 20 per account the configuration assumes; one of the three accounts was refused at login on almost every proxy exit (1 success in 19 attempts), although it logs in normally without one; and the retry logic spent daily searches twice on the same case.

Starting point

What was handed over

The repository is a Python 3.14 application that drives regular Google Chrome through Playwright. It logs into the CBRS portal with three named accounts (ejecutivo_1, _2, _3), routes each account through its own DataImpulse Mobile proxy port in Chile, searches the commerce index by foja, número and año, downloads the page images and assembles one PDF per result. Jobs are kept in a local SQLite queue.

As delivered, it was built to run as an always-on service: first as native Windows scheduled tasks, then migrated to systemd inside WSL on another machine, with a separate process that owns the Chrome windows. For this review the goal was simpler: run it on a Linux machine, without any service, as a component to be called from another codebase.

The contractor's own notes, dated 8 Sep 2026, already recorded that the migrated setup was incomplete: “one account completed a new search and PDF download; two accounts are still receiving the portal's generic login rejection.” The per-account quota of 20 searches a day is described in the README as a theoretical figure (“cupo teórico”) to be aligned with the contract.

Problem register

Every problem found, and what was done

Grouped by where the problem sits. “Fixed” means changed in code; “workaround” means it was avoided without changing the code; “open” means it still affects results.

In the delivered code and configuration

P1
Code defectFixed

Chrome crashed on every launch on Linux

What happened
Every account's Chrome exited immediately with FATAL … Socket path too long, so no login or search could start.
Cause
The code forces Chrome's temporary folder inside the repository. Chrome creates a socket there, and Linux caps socket paths at 107 characters; at this checkout's location the path came to 108. The previous host only worked because its folder path happened to be shorter.
What we did
Changed cbrs/paths.py to fall back to a short, private folder under /tmp when the in-repository path would be too long. Updated two tests and added two; the suite passes (471 of 472, the remaining failure being the pre-existing Windows-only test).
P2
Code defectWorkaround

The worker ignored the account credentials in the configuration file

What happened
The first run failed for every account with “requires environment variable(s) … USERNAME, PASSWORD”, although both were set in .env.
Cause
Proxy and solver settings are read from .env, but account credentials are read only from the process environment. The old service injected them through a launcher script; running the documented command directly skips that step. The docs don't say so.
What we did
Every run goes through deploy/run_with_env.py .env -- …. Any integration has to do the same or pass the variables itself. A related trap: values in .env override environment variables, even when blank.
P3
ConfigurationWorkaround

Configuration templates contradict each other

What happened
The Linux installer copies a template for a different proxy type (one static proxy URL per account, different variable names). The layout actually used in production lives in a different example file. That example also enables a mode that requires the separate Chrome-owner service.
What we did
Wrote a working .env and account-pool file by hand from the production layout and removed the service-only mode. The code rejects an account that mixes the two layouts, so a copied template does not work as-is.
P4
ConfigurationWorkaround

The CAPTCHA solver blocks startup and, per the contractor's own notes, does not help

What happened
With a 2Captcha mode selected, every command refuses to start until an API key is present. The contractor's debugging notes (29 Aug) record that every 2Captcha token was rejected by the portal while the browser's own token was accepted.
What we did
Ran with the solver disabled (browser-only reCAPTCHA). No paid solves were used. The load run did not show CAPTCHA as a limiting factor.
P5
OperationsWorkaround

One account's proxy route was dead, and changing it required editing the database

What happened
ejecutivo_3's route (port 10002) timed out on 3 of 3 checks, so the account could never be approved.
Cause
A mobile proxy port maps to one device, which can go offline. The active port is stored in the local database and overrides the configuration file; the built-in command to change it only works while the always-on service is running.
What we did
Moved the account to port 15215 in both the database and the pool file (safe: the account had never logged in). Checks then passed.
P6
Code defectOpen

Retries spend the daily limit twice on the same case

What happened
12 times the code decided the search form “did not submit within 15 seconds” and moved the case to another account. At least two of those were in fact recorded by the portal: Foja 37684 · 2007 and Foja 79769 · 2014 appear in ejecutivo_1's portal history although the code logged them as not sent, and both were then searched again on ejecutivo_3. The stuck test case 47092 likewise shows up in both accounts' histories.
Effect
ejecutivo_1 used 9 portal searches to deliver 6 cases. With a limit of 7–9 a day, every duplicate costs about 12% of an account's day.
Status
Not changed. This is the most valuable fix to make before any further volume testing.
P7
ConfigurationOpen

The configured daily quota does not match the portal

What happened
The code allows 20 searches per account per day (60 across three). The portal stopped both working accounts well before that, so the code's own limit was never reached and its capacity figures overstate what's available.
Status
Not changed. The real figure should come from the CBRS contract; the observed value is 7–9.
P8
DocumentationOpen

Documentation disagrees on how the system is meant to run

What happened
The README describes native Windows as the active setup and forbids WSL; the maintenance rules and Linux guide say WSL is active and Windows is only a fallback. None of it covers running without the service, and there is no guidance for calling it from another application.
Also found
Python 3.14 is required but not packaged for Ubuntu 24.04; one test fails on any non-Windows machine; when no account can proceed, the worker keeps re-checking the queued cases every few seconds (119 times in 8 minutes). None of these changed the results.

On the portal's side

P9
PortalOpen

The portal stops each account after 7–9 searches a day

What happened
ejecutivo_1 was stopped at 22:04 and ejecutivo_3 at 22:07, both with the portal's own dialog. The portal's recent-searches panel listed 9 inscriptions for the first account and 7 for the second at that moment.
How the code reacted
Correctly: it recorded a hold on each account, stopped using it, and kept the remaining cases queued rather than failing them.
“Se han agotado las consultas disponibles por hoy.”Portal dialog shown to both accounts on reaching the limit
P10
PortalOpen

One account is refused at login on most proxy exits, though its credentials work

What happened
During the runs, ejecutivo_2 was rejected 11 times with HTTP 400 and the portal's generic intente-mas-tarde (“try again later”) code: on its own proxy port and on three replacement ports the code tried automatically (12595, 15432, 14154).
Follow-up tests
On 11 Sep the same account logged in on the first try from the workstation's own Chilean connection, with no proxy (HTTP 200). Minutes later, a login through the exact proxy exit that ejecutivo_1 logs in through without trouble (port 10000) was refused with the same generic message.
Proxy probe
A controlled probe then tried one login per fresh DataImpulse exit, two minutes apart. Six were refused with the same generic message, on exits of four different carriers (WOM, Telefónica, Telmex, Entel); one failed before the login page loaded; the eighth, a WOM exit in Santiago, logged in normally (HTTP 200). Before that, the session from the direct login was still accepted through the account's own proxy port, so the portal does not tie a session to the connection it started on.
What it means
The credentials are correct and the account can work through proxies, but its logins succeed on very few exits: 1 in 19 proxy attempts across the review, while the other two accounts were usually accepted. The carrier is not the deciding factor, since WOM exits were both refused and accepted. The refusal is made by the portal's application, not its firewall: every request passed the Imperva service in front of the site, Google's reCAPTCHA loaded normally each time, and the refusal came back as the application's own error message. That pattern is most consistent with a risk score computed for each login attempt (for example reCAPTCHA Enterprise, which the portal uses) that this account fails far more often than the others, possibly because of its history of failed attempts. The portal never states the reason, so this remains an inference.
Context
The contractor's notes from 8 Sep describe the same rejection on two accounts and state it is not evidence of a wrong password. It was a known, unresolved issue at handoff.
P11
PortalIntermittent

The portal refuses individual searches with a generic error

What happened
6 searches (5 on ejecutivo_3, 1 on ejecutivo_1) were answered with the portal's dialog “Se ha detectado un problema, refresque la página e intente nuevamente.” The same case later succeeded, so this was not about the inscription itself.
How the code reacted
Paused the account for a few minutes and tried another account. The contractor's notes associate this response with the connection route rather than the account or query.

The core question

Why 30 cases with three accounts didn't get through

Configured60 / day

20 searches per account × 3 accounts, the figure the configuration and README assume.

Best case at observed limits21–27 / day

7–9 per account × 3, with every account logging in and no duplicate searches. Still short of 30.

Actual13 / day

Two accounts working, one refused at login through the proxies, and at least 3 searches spent on duplicates.

The shortfall is not one bug. At the limits the portal enforced, three accounts cannot cover 30 inscriptions in a day even when everything else works. On top of that, one account in three could rarely log in through the proxies and the retry logic wasted part of the remaining capacity. Clearing the 19 queued cases at the current rate takes about two more days.

What did work reliably: every accepted search produced a complete PDF (13 files, 43 pages, all valid), no case was marked failed or lost, and the code stopped cleanly on the portal's limit instead of pushing past it.

Changes

What was changed during the review

  • Code: cbrs/paths.py (Chrome temporary-folder fallback, P1) and tests/test_repo_paths.py (two tests updated, two added). Committed with this report on branch handoff-review-fixes; not pushed.
  • Local configuration (never in git): a .env for three accounts, DataImpulse Mobile and browser-only CAPTCHA; an account-pool file; ejecutivo_3's proxy port moved from 10002 to 15215 in the pool file and local database.
  • Environment: Python 3.14.7 in a local virtual environment for the repository.
  • Not changed: retry and quota logic (P6, P7), credential loading (P2), templates and documentation (P3, P8).
Recommendations

What it would take to reach 30 cases a day

  1. Confirm the per-account daily limit with CBRS and set the code's quota to it. At the observed 7–9, 30 cases a day needs four to five working accounts, not three.
  2. Fix submission detection before moving a case to another account (P6), so a case is never charged to two accounts. This is the cheapest capacity gain available.
  3. Treat logins as the scarce step and keep sessions alive. ejecutivo_2 logged in on 1 of 19 proxy attempts, but once logged in its session was accepted through other exits. Log in rarely and patiently (one attempt per exit, minutes apart), reuse the session instead of logging in again, and ask CBRS how they assess logins from mobile or proxy connections.
  4. Make it usable as a component: read credentials from the configuration file, document one supported way to run it without the service, and remove the contradictory templates and platform instructions.
  5. Re-run the remaining 19 cases after the accounts' limits lift, and repeat the load test once the fixes above are in, to measure a clean per-account figure.
