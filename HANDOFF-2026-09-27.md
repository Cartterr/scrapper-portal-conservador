### Fixes in `76ef7f1`

- **D28 (`cbrs/form_search.py`, `cbrs/runtime_logic.py`):**
  - The problem: a due quota probe ending without a quota answer used up its hourly slot.
  - Now `restore_quota_check()` gives the slot back when the probe ends with any stop in
    `PROBE_UNANSWERED`: auth_required, search_not_submitted, captcha_rejected,
    captcha_solver_failed, or temporary_unavailable (covers the portal error dialog).
  - The pre-submission dialog check and the probe reload were moved inside the `try`,
    so they are covered too.
  - Text (non-fna) jobs get the same restore.
  - Test: `tests/test_portal_quota.py::test_probe_without_quota_answer_keeps_its_admission`.
- **D27 (`cbrs/api.py`):** `REPORT_FIELDS` now includes `resume_at`, so the `get-batch`
  CSV has the column.
- **D29 (`cbrs/config.py`):** `DEFAULT_HEADLESS = False`. `.env.example` and the README
  point to Xvfb.
- **D30 (`cbrs/cli.py`, `cbrs/browser_owner.py`):** `cbrs jobs worker` (exit 2) and the
  external owner refuse to start headless, with `HEADLESS_UNSUPPORTED`. The reason:
  headless searches get `captcha-rechazado` plus the portal error dialog, which the
  service treats as a compromised route and answers by deleting profiles.
- **D31 (`cbrs/jobs.py`, `cbrs/browser_session.py`):** the root cause was Playwright's
  sync loop `while not task.done(): dispatcher_fiber.switch()`.
  - A KeyboardInterrupt raised inside the dispatcher greenlet kills it, and every later
    Playwright call spins at 100% CPU. That's why Ctrl+C hung the worker mid-login.
  - Fix: `_interrupt()` handles SIGINT and SIGTERM and throws KeyboardInterrupt into
    the caller greenlet. A SIGINT that was ignored at launch stays ignored.
  - Chrome now launches with `handle_sigint=False`.
  - Reproduced with real Chrome on Linux: 97% CPU spin before, clean exit in 0.5 s after.
- **Point 6 (`cbrs/config.py`, `cbrs/jobs.py` `begin_dataimpulse_rotation`):**
  `CBRS_DATAIMPULSE_MAX_CANDIDATE_LOGINS_PER_DAY`, default 10.
  - Counts candidate logins in the last 24 h, excluding outcomes in
    `NO_LOGIN_CANDIDATE_OUTCOMES`.
  - When the cap is hit, the account stays `retry_allowance_exhausted` until 24 h after
    its oldest counted login.
  - The default is 10 because an older test requires recovery to reach an 8th exit.
- A `SyntaxWarning: "\d"` in `form_search.py` (the Recientes JavaScript) was fixed.

### Request log (`cbrs/request_log.py`, hooked in `BrowserSession.open`)

- **Where:** `<log_dir>/requests/<account>/<UTC date>.jsonl`, by default
  `.cbrs/runtime/logs/requests/...`. Plain files, not SQLite.
- **One line per recorded request:** `at, method, host, path, type, status` (or `failed`),
  plus the session: `client, profile, port, headless`.
- **What is recorded:**
  - Every portal (`*.conservador.cl`) page load or API call: types document, xhr, fetch,
    other.
  - reCAPTCHA scripts, frames and API calls on google.com / gstatic.com / recaptcha.net.
  - The proxy health check's `POST /api/v1/home/start`, made outside Chrome, as
    `type: health, client: proxy_health`.
- **Never stored:** query strings, headers, cookies, bodies. Path segments of 24+
  opaque characters are masked as `:id`.
- **CLI:** `cbrs requests ACCOUNT [--since ISO] [--until ISO] [--json]` prints counts
  per method, path and status.
- **Tests:** `tests/test_request_log.py`, including a real-Chrome test with routed fake
  portal pages.
- **Limits:**
  - It records what this install sends, not other people using the same account.
  - It records the proxy port, not the exit IP.
  - Portal error codes stay in the event log, not in the request log.
  - Files are never pruned (a `ponytail:` note marks it).
- **Open design question:** the proxy health check sends user-agent
  `Mozilla/5.0 cbrs-proxy-health/1.0` to the portal API from the same exit the account
  then logs in from. The operator hasn't decided whether to change or drop it.

## 5. The ban experiment on OUR dev accounts (running)

- **Goal:** reproduce the client's 09-24 pattern until one of our accounts gets banned,
  to learn the cause. The operator's instruction: "continue till one gets banned".
- **Location:** `/var/tmp/cbrs-banexp/`, which survives reboots.
  - `code/`: an rsync copy of the repo at `18d941b` plus `code/banexp.py`, the harness.
  - `arm.sh`: the runner.
  - `log.jsonl`: all results.
  - `state.json`: ports and sessions.
  - `profiles/`, `shots/`, `pool/`.
  - `used-ports.json`: production's ports, never reused.
- **Isolation:** uses its own settings root, profiles, quota store and separate Xvfb
  displays, plus fresh DataImpulse sticky ports. It only reads the production `.env`
  and `account-pool.json`, and never touches production browsers.
- **Timers:** persistent units `cbrs-banexp-headless.{service,timer}` and
  `cbrs-banexp-logins.{service,timer}` in `/etc/systemd/system`. Each run also logs
  production's `account_checks` view read-only (`event: production_view`).
  - **Headless arm, `ejecutivo_3`, every 60 min:** reopen its logged-in profile headless
    and try 2 searches, then one fresh headful login on a new exit as a ban detector.
  - **Login arm, `ejecutivo_1`, every 30 min:** 3 fresh headful logins on new exits.
  - **Control:** `ejecutivo_2`, untouched.
- **Stop condition:** a login answered with `CredentialsRejectedError` or HTTP 401 writes
  `/var/tmp/cbrs-banexp/BANNED`; `arm.sh` then stops the timers.
- **Results as of 2026-09-27 19:40 UTC: no ban.** 37 cycles.
  - `ejecutivo_1`: 69 fresh logins, 27 OK. The rest were exit-related failures:
    captcha-rechazado 17, solver refusal after a rejection 21, auth_required 4.
  - `ejecutivo_3`: 18 headful logins OK, 10 headless session reopens OK. Headless
    searches almost always get captcha_rejected or the error dialog: 4 captcha_rejected,
    9 temporary_unavailable, 6 search_not_submitted.
    **One headless search succeeded on 09-27 18:56 UTC** (port 19299).
  - Production's own sessions were unaffected throughout.
- **Earlier manual steps (09-25):**
  - Headless login was rejected where headful passed on the same IP.
  - Headless searches in a logged-in session triggered exactly the client's error dialog,
    and afterwards headful searches from that same session and IP got it too.
  - Fresh logins right after were fine.
- **Check:** `wsl.exe -d Ubuntu-24.04 -u root -- tail -f /var/tmp/cbrs-banexp/log.jsonl`
  and `systemctl list-timers 'cbrs-banexp-*'`.
- **Stop it:** `systemctl disable --now cbrs-banexp-headless.timer cbrs-banexp-logins.timer`.
  Remove the 4 unit files from `/etc/systemd/system`, then `systemctl daemon-reload`.
  Delete `/var/tmp/cbrs-banexp` when no longer needed; it holds Chrome profiles
  logged into our dev accounts.
- **Proposed next arm (not started):** the shared-IP test, i.e. two of our dev accounts
  logging in through the same exit, the top suspect from section 4.
